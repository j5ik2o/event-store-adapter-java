# Explicit blocking execution: core resource

`BlockingExecution` implements the core resource from the adopted [ADR0010](https://github.com/j5ik2o/event-store-adapter/blob/e4c0fdafe7fd6f9b6c92ff12a5f99485b5e406b1/docs/adr/0010-explicit-execution-for-async-operations.md). It is the first core unit of #818. `SqliteEventStore.createOffloaded` is the first backend factory; Spanner and Bigtable factories are follow-up work. Existing factories keep their behavior.

Create a resource explicitly with `BlockingExecution.singleWorker(Q)`, where Q is positive. The application owns it. One non-daemon worker executes entire operations in accepted FIFO order, with one active position and Q pending positions. `submit(Callable<T>)` is the minimal backend integration boundary; pass the complete synchronous operation including validation, serialization, transaction resolution, post-commit work, retention, listeners and cleanup. Admission does not inspect payloads or invoke operation code. Full or closed admission returns a failed `CompletableFuture` with `RejectedExecutionException`. There is no global pool, caller execution fallback, or wait for queue space. Short synchronized bookkeeping can wait for the monitor; this is not a hard latency guarantee.

Keep inputs unchanged until the actual operation ends. Successful cancellation before the atomic RUNNING transition skips invocation; failed cancellation after consumer completion or timeout leaves accepted work eligible to run. Cancellation reserves a queued command under the lane monitor, then attempts Future cancellation outside it. A worker encountering that reservation helps finish the same cancellation before choosing whether to run. This arbitrates against Future completion without executing user callbacks under the monitor. For a skipped command, its queue slot remains charged until the worker removes it. Cancelling an in-flight result with either flag never interrupts the worker, rolls back a transaction, releases the lane or proves an operation has ended.

The resource clears its Callable reference after invocation cleanup, before publishing the result, and when the worker removes skipped work or recovery fails pending work. In-flight result cancellation retains inputs until actual operation exit. Retaining a result may still retain values or causes returned by the operation itself.

`close()` closes admission idempotently and returns without waiting. Accepted work drains. Await `drained()` from outside the worker before closing storage or SDK clients that no other user still needs. The read-only stage includes operation cleanup and worker-run result callbacks. Consumer completion or cancellation of a derived future does not change the library's termination state. Try-with-resources closes admission only.

Callbacks may run inline on the completing worker, or on a caller attaching to an already completed future. A stalled operation or callback stalls the lane and drain. Reentrant admission is allowed within capacity. Never synchronously wait for another operation or drain from code running on the same lane. Use a separate explicit executor for blocking continuations.

Ordinary operation exceptions remain the cause of the failed result. Controlled `Error` attempts exceptional result completion, unwinds cleanup, and is rethrown to the worker's uncaught handler. After that handler returns, a replacement worker continues accepted FIFO work. If replacement fails, pending results and drain fail diagnostically and admission closes. Fatal VM failure cannot guarantee recovery or cleanup.

This unit has no storage SDK dependency and does not close storage. Spanner and Bigtable operations and their opt-in factories, wrapper runtime, long-running load and the full D8 matrix remain gates in #818. Core test results are not independent review, CI completion, or publication approval.
